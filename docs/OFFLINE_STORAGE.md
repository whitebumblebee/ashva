# Offline content and learner storage

Storage was introduced in Android v0.3.0, the sourced catalog in v0.4.0, and versioned repertoire choices in v0.5.0. It uses Room KMP 2.8.5, bundled SQLite 2.7.1, KSP 2.3.12 and coroutines 1.11.0. Versions were checked against official releases on 2026-10-01; Room 3's alpha documentation is not a reason to silently adopt an experimental library. Room's generated expect/actual constructor still produces Kotlin's expect/actual-class Beta warning. Both shared iOS targets must compile; there is no iOS app/runtime validation yet.

## What users can do

- The reviewed opening-name pack installs locally on first launch in v0.9.0. On Learn, **Offline library & sources** shows its state and retry controls; install January and/or April 2020 broadcast packs there separately. These packs are included in the APK and installed into SQLite without a server, network or account. This is **not** a new live download provider.
- Each pack shows Not installed / Installing / Installed / Installation failed, source attribution, version, license and scope. An update failure can retain an older available pack. The app does not claim the data packs are finished teaching courses.
- Study/practice an authored or installed sourced lesson, choose a branch/color/cursor and return to Learn. Wait for **Saved for offline resume** before force-stopping. Relaunch and tap **Continue learning**: the selected line, branch-return stack, color, cursor, mode, hint and assistance context restore. Playback never resumes automatically.
- Actual attempted moves are recorded with outcome, color, route, cursor and assisted status. Android0.15 adds chosen-scope recall schedules and real Home/Review/Profile events; legacy attempts remain ungraded, not retrospectively converted to mastery. See [recall contracts](RECALL_REVIEW.md).
- **My repertoires** lists real saved family/color policies. The board editor seeds a chosen route, saves preferred learner moves and included opponent replies, and shows finite snapshot gaps. Policy practice uses only fitting routes; broader exploration remains intact.
- In v0.10.0, named sets pin exact family revisions and support an interleaved practice queue after coherence/availability checks. Set membership is explicitly saved; current family edits do not silently update it. Old set revisions and bookmarked queue indices remain available after cold reopen.
- Android0.13 adds Players & GM games: a lazy metadata shelf, local follows/private PGNs and original mainline replay with exact retained-source bookmarks. Private imports never affect public counts. Complete verification is in Relay0028; see [library behavior](GM_LIBRARY.md).

The main catalog in v0.9.0 contains 149 guided courses with all 3,815 source routes and 78 original illustrative study continuations. Family plans and rules-derived move explanations are generated locally, without changing source records or creating historical annotations. Versioned `course:v1:` lesson IDs keep the old seed and source lesson IDs, moves, fingerprints, policies and bookmarks intact. Explore's **Starter** and **Sourced** filters retain those legacy views; raw source routes still have no reviewed strategic annotations. SQLite can also store 857 accepted January and 79 April original broadcast scores (936 total), but a GM-library entry point is still upcoming. January's 95 quarantined inputs never enter score observations; all dispositions remain in the immutable pack. Scores with a known result and legal moves are not independent historical-completeness proof.

The common SourcedOpeningCatalog maps validated records to source-labeled presentation models without dropping routes; TeachingCatalog constructs the separate guided presentation. Android loads/decodes/coaches them and prepares legal family graphs on background dispatchers with cancellation checks. A single immutable presentation is reused in the app process only when its manifest checksum and teaching version match; cold process launch rebuilds it. It contains no learner state. Search labels and graph fingerprints are cached; at most eight heavy source/course family graphs are cached, separate from seeds and any active replay object. UI continuation lists show twelve at a time with an explicit Show more action; the graph retains every path. Current family maxima fit the bounded graph contract (1,000 paths / 50,000 half-moves). A future oversized family is rejected visibly, not silently truncated. Source and course IDs include the immutable pack ID; a no-longer-active/missing version reports unavailable and preserves its bookmark rather than resuming against different content. Retained-version lesson selection is not implemented yet.

The 0.11.0 larger snapshot fits existing limits: 628,586 compressed bytes, 4,147,031 decoded bytes and 3,838,438 derived game-payload bytes; both installed samples total 82,679 half-moves. No size/index bounds, schema or original pack bytes were raised/changed. Its trusted catalog hash and exact retained taxonomy dependency are verified before atomic activation, including cold reopening.

Legal notation parsing returns one checked move/notation/history-aware transition instead of reapplying it for each field. Immutable parsed games reuse one checked position sequence; already-unannotated canonical scores retain it. Installation uses that per-score replay for payload/endpoint/normalized-position/taxonomy checks, then releases board states rather than caching all game graphs. Dependency hashes are still rechecked in the atomic transaction. Repetition, castling/en-passant/promotion and supplied metadata checks remain; neither efficiency nor a worker thread certifies representative-device performance.

## Ownership and contracts

Android v0.6.0 adds `LearningStore.games(packId?)`: active game records by default, or an exact retained immutable pack. JSON decoding and shared `ObservedReplyIndex` legal aggregation run on a worker, with cancellation checks. A single in-memory index is keyed by active broadcast pack IDs/manifest hashes, rebuilt after cold launch or version changes, and discarded when that sample becomes unavailable. Missing/loading/error/ready-zero states remain distinct; stale work cannot publish counts from a withdrawn version. No database table/migration or learner write is required. The bounded index accepts at most 32 packs, 10,000 input score rows and 500,000 input half-moves; oversized input fails visibly, not by truncating. First-visit score-ID denominators and source attribution are documented in [opening coverage](OPENING_COVERAGE.md). Wider populations will require revisiting mobile memory/indexing and release scope rather than silently shipping a whole corpus.

`shared/.../storage/LearningStore.kt` is the platform-neutral repository boundary. `RoomLearningStore` supplies the implementation; Android/iOS/JVM have database and SHA-256 adapters. Android owns a single store through `OpeningLabApplication` and injects it into the screen ViewModel. The existing SavedStateHandle remains a fast Android recreation path, while portable replay snapshots persist in SQLite for cold reopen. Writes are asynchronous and ordered/conflated for the latest bookmark; wait for the visible saved confirmation before terminating the process. An action killed before its save completes may restore the previous bookmark.

Tables separate immutable versioned packs/content/position indexes/notices/annotation slots from bookmarks, attempts and repertoire selections. Learner rows have **no foreign keys into replaceable content**. A changed lesson fingerprint is not resumed against incompatible moves; the bookmark/history are retained and the app reports changed/unavailable content. No old pack versions are automatically pruned. Annotation slots are empty because this snapshot supplies no reviewed teaching annotations or engine lines. Original source annotations remain in the raw pipeline inputs, not invented in the mobile store.

`repertoire_policy_versions` retains immutable `(id, revision)` payloads and `active_repertoire_policies` points at each latest revision. A writer transaction accepts revision zero or the exact next revision; stale/conflicting writes are rejected, identical retries are idempotent and cannot roll the pointer backward. The editor disables changes while saving and retains the previous saved state on failure. Payloads are schema/bounds checked (2 MiB), then graph/version/side/move validated by the shared repertoire model. Policies use normalized positions but coverage traverses finite original move-order prefixes, not an infinite cyclic position graph. A separate moves-only content hash avoids rebinding to changed moves while allowing narration edits.

Bookmarks optionally reference an exact policy ID/revision. Cold restore loads that retained revision, reconstructs its restricted graph, checks the lesson fingerprint and restores the original replay/branch context. Existing bookmark JSON fields default to null; legacy active-route rows are kept, not auto-converted into repertoire policies. Old revisions are deliberately retained and may grow storage; pruning/export/version-management UI remain future work. Missing/inactive content still retains policies/bookmarks rather than deleting them.

Schema 4 adds `repertoire_set_versions` and `active_repertoire_sets`, using the same immutable-next-revision transaction contract. A set names 1–64 unique family policy IDs/revisions of one color; saves check every retained policy revision atomically. Its current pointer cannot be rolled backward by an idempotent retry. Bookmark set ID/revision/index fields default to null for legacy JSON. Cold resume rebuilds a deterministic admitted-route queue and validates that the bookmarked root path and policy are the exact queue entry; changed/missing content is reported, not rebound. Sets neither stitch new move orders nor turn route visitation into mastery.

## Installation, interruption and rollback

Each queued bookmark carries its own request revision. An older completed write cannot report the newest Saved state while a later conflated write is pending; a controlled-delay native fixture tests this. Game/opening bookmarks share one serial writer.

1. The Android adapter reads bounded assets on an IO dispatcher. Only three reviewed pack directories are packaged through AGP's generated-source variant API; raw archives and arbitrary future packs are excluded.
2. The manifest SHA-256 must match the separately pinned app catalog. Schema/processor, exact filenames, collection license, byte/count bounds, every payload checksum, legal SAN/UCI/FEN replay, unique IDs, source locations and disposition/depth counts are validated before activation. A checksum pins integrity, not independent authenticity or a cryptographic signature.
3. Game naming requires the exact installed taxonomy pack ID **and manifest hash**. The consumer recomputes the last known taxonomy match against that retained dependency, not whichever newer taxonomy happens to be active.
4. One SQLite immediate transaction inserts all content/index rows and switches the source's active pointer plus installed status. Exceptions/cancellation roll back every partial row. Previously active content and learner state stay intact. Reinstalling identical bytes is idempotent; reusing an immutable pack ID with different bytes is rejected.
5. A persisted LOADING job found at startup becomes ERROR with a retry message. App-process death before commit leaves the old active version; after commit it leaves the new complete version. Library checks expose errors; no destructive reset is attempted.
6. `activatePreviousVersion(sourceId, packId)` atomically reactivates a retained version after checking its source and exact dependencies. The repository/tests support rollback; no user-facing version-management UI or remote pack transport is included yet. Keep dependencies when eventually implementing pruning.

Bounds: manifest 64 KiB; each payload 8 MiB; total declared payload 12 MiB; at most 50,000 opening/issue records and 10,000 games; 512 KiB per JSONL row. Existing source validation further limits moves/PGNs. Validation runs away from the main thread. This is a bounded installation slice, not a performance claim for a multi-million-game catalog.

## Database migration and verification

Exported schema1 is a **pre-release fixture**, not a previously shipped Room database. Explicit1→2 adds notices;2→3 policy tables/index;3→4 set tables;0.13's4→5 adds `followed_players` and `private_games`;0.15's5→6 adds recall cards/scopes/membership/active pointers/events and separate Study views. Android/JVM/shared iOS register all five migrations with no destructive fallback. Real exported-schema1–5 SQLite fixtures migrate to6 while preserving bookmarks, attempts, selections, pack pointers/notices, policies, sets, follows and private imports. No row is repurposed/pruned or old attempt backfilled into mastery. Defaulted bookmark JSON retains assistance and exact review/event references. Original-game bookmarks pin exact retained pack/manifest/record (or private identity), never a newer active pointer. Private imports stay outside public packs/observations; see [library behavior/bounds](GM_LIBRARY.md). Future versions need explicit migrations and preservation fixtures.

JVM repository tests cover empty/missing state, cold reopen, learner selections/attempts/bookmarks, idempotence, immutable-ID/schema/checksum rejection, missing files/dependencies, atomic failure/cancellation after row insertion, abandoned loading jobs, updates/rollback/progress retention, real pack installation and exact dependency retention. Catalog tests enumerate all 3,815 routes and replay every Ruy Lopez route from both colors. Compose instrumentation covers bundled installation/licensing, sourced search/route/branch controls and fresh database/ViewModel restoration without a SavedStateHandle bundle, plus actual assisted attempts and transposed source identification.

**Run connected tests on an isolated emulator/device.** The Gradle test runner may uninstall its target APK and delete its data. With an isolated device already running, select its exact serial:

```bash
ANDROID_SERIAL=emulator-5556 ./gradlew :androidApp:connectedDebugAndroidTest
./gradlew :shared:jvmTest :shared:testAndroidHostTest :contentTools:test
./gradlew :androidApp:assembleDebug :androidApp:lintDebug
./gradlew :shared:compileKotlinIosSimulatorArm64 :shared:compileKotlinIosArm64
node --test scripts/fetch-content.test.mjs
./gradlew :contentTools:run --args=verify
```

Confirm the Gradle output names **only** the intended isolated device. Do not clear data or uninstall on the user's learning install. Use `adb -s <exact serial>` when more than one emulator is running.
